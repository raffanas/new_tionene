## Major gaps to address **in v0.1.40 before treating it as the authoritative developer execution brief**

### P0-1. Selective impact propagation is NOT fully specified — **highest priority**

**Evidence:** The latest `07_v0.1.38_Owner_Approved_Changes.md` protects manual edits and mentions affected-record warnings; `02_Functional_Requirements.md` (`CON-009`), `03_Data_Architecture_and_Rules.md` §8 and `04_Decisions_and_Open_Questions.md` (`OQ-15`/`OQ-16`) still describe automatic changes or defer granular synchronization details. **They do not fully express the owner's newly approved 0-to-all, arbitrary-subset update selection.**

**Needed:** an explicit cross-app common change framework. For each edited record, detect declared affected fields/records (upstream and downstream where modeled), preview **old → proposed** values, allow **none, any subset, or all**, then save only selected changes. Preserve existing manual overrides by default, never silently reactivate automation; allow Admin to apply a proposed recalculation to a specific overridden field explicitly. Review warnings are **nonblocking**, including if paid/confirmed records diverge. Audit every chosen action and leave meaningful `Changed / Needs Attention` tasks until Admin dismisses. Define behavior when some targets cannot be computed, when edits are concurrent, and when a selected update fails: do not partially hide a failure or corrupt ledger entries. Distinguish **data field updates** from real-money corrections, where original transactions remain immutable and an adjustment/reversal must be logged.

**Critical practical test:** Change one booking field that would affect five fields; successfully select 0, 1, 2, 3, 4 or all 5; previously overridden supplier cost stays unchanged unless specifically selected; completed cash movements remain intact.

### P0-2. Manual-first fallback and recoverability must be a top-level architecture/acceptance rule

**Evidence:** Manual adjustments, unknown-cost fallbacks and independent records exist across `01_*`, `02_*`, `03_*` and `07_*`; however, v0.1.39 has **no unified, testable promise** that every critical workflow still operates when its corresponding automation fails or cannot resolve an input.

**Needed:** Admin must independently be able to **create/correct** arrivals, bookings, payables/costs, supplier confirmations, guest-wallet fields and actual financial entries, while leaving other records untouched. Where auto-create, region detection, rate matching, PDF prefill or readiness computation fails: report the local error, keep the partially entered real data, allow immediate manual completion, and offer a retry that **cannot duplicate** bookings, receipts or payments. The manual path must be simple and visible only when needed. Document no-code Admin settings capabilities and safe non-configurable core identity/authorization/money-integrity fields. Prioritize **usable vertical workflow first**, automation enhancements second.

**Critical practical test:** Simulate failed automatic arrival/reservation generation after a seller finalizes; Admin manually creates the missing reservation and payable, records a genuine payment, and gets a usable wallet, without duplicate creation after retry.

### P0-3. Contradictory 'active' instructions must be reconciled, not just overridden by a preface

**Evidence:** `00_READ_FIRST_CURRENT_AUTHORITIES.md` correctly gives precedence, but `02_Functional_Requirements.md` `CON-009` and `03_Data_Architecture_and_Rules.md` §8 retain older wording for protected update behavior; `04_Decisions_and_Open_Questions.md` still includes old `OQ-28` receipt-correction uncertainty, `OQ-34` unresolved migration and historical open supplier-field language; `Data/DEVELOPER_IMPORT_NOTES.md` retains historically true but now misleading 'Dolphin transport out of scope' and 'Xcaret annex not in ZIP' statements above later overrides. `README.md` still displays **Version 0.1.38** in its main status line.

**Needed:** A clear **single current specification** and readable **START HERE** guide; update the active requirement/architecture/decision tables directly, move superseded text under labelled history, correct all version headers, and ensure a developer/code agent cannot accidentally implement incompatible rules. Preserve all source XLSX and historical decision evidence unchanged.

**Critical practical test:** Search active docs for 'automatic downstream update', 'approval required before seller revision', 'deposit corrections seller unknown', 'Dolphin transport unavailable', 'hotel list not packaged', or 'Xcaret images missing'; any such statement must be removed from active instructions or explicitly marked historical.

### P0-4. The real working app needs an executable technical/finance/security gap check

**Evidence:** `10_v0.1.39_Verification_Report.md` expressly disclaims repository, database/auth, real supplier-link privacy, rendered PDF, persisted financial ledger, actual imports and executing all 167 scenarios. This is **a developer implementation gate, not missing owner-approved supplier data**.

**Needed:** Before modifying code, developer inventories existing routes, DB tables, auth and migrations; maps **implemented / partial / missing** to requirements; builds the shortest reliable contract → arrival → reservation → client receipts + provider payable/payment → wallet → reports path. Prioritized end-to-end tests must cover record-idempotency, immutable receipt/refund history, native MXN liability vs USD estimate vs actual paid USD, double-count prevention for Dolphin transport, archived supplier-rate snapshots, and secure single-reservation token access (including revocation, cross-booking attempts and protection of CPF/internal notes). Demonstrate generated contract PDFs with **multiple hotels, tours and payments**, preservation of previously issued versions, and separate upload of signed files; do not implement fabricated/in-app signatures. Do not claim a verified application from verified spreadsheets.

**Critical practical test:** Use an ordinary multi-tour, multi-hotel, partial-payment test arrival end to end; deliberately override a paid payable without changing actual cash; confirm operational output and financial reports are still honest and usable.

## Significant but narrow functional decisions to make during implementation (not reasons to reopen all pricing)

### P1-1. Infant counts must flow from the customer sale, not appear only downstream

`CON-012` and `RES-019` still explicitly say **adult + child** sold-line counts, while v0.1.39 reservation and Dolphin transport require **adult + child + infant** by service. Unless seller sale capture has a per-service infant count (zero by default or explicitly unknown), the reservation/transport cannot reliably auto-populate. **Recommend adding a per-service infant field** in the simple seller input and carrying it through contract, reservation, wallet and transport pricing. **Do not invent an infant supplier base-ticket cost** where the 80-rate schema provides only adult/child prices; mark unsupported infant base-price treatment for Admin review. This is a design recommendation awaiting owner confirmation if its seller UI materially changes.

### P1-2. Client-facing tour inclusions/exclusions are not supplied as a complete catalog

`CAT-007`, `OQ-08` and `Contract_Generation_and_Field_Map.md` correctly avoid fabricating these descriptions, but the 52-product XLSXs do **not** supply complete approved customer inclusions/exclusions. Contract PDF content cannot be automatically generated completely until Admin enters the text or seller adds accurate text for the sold service. **Require a clear manual per-tour text fallback and missing-copy warning**; build a reusable editable catalog text field, then fill common services incrementally. No bulk rewriting/legal review required now.

### P1-3. Wallet readiness minimum and future Xcaret fallback are configurable startup decisions

The wallet's **visual style** is properly deferred, but Ready should have a minimal functional completeness rule (confirmed required bookings + current wallet prepared, with no fabricated unknown pickup/code). The precise printable required fields/default warning need a developer proposal and owner's UAT review, not a new design project. For 2027 Xcaret, dates stay selectable; where existing regular/high prices differ, **Admin must select the provisional season/rate** in setup or per booking; no hardcoded season assumption, and supplier availability remains unverified until confirmed. These are startup configurations and manual alternatives, not fresh historical pricing research.

### P1-4. Provider-specific exceptional booking details are expected to be Admin-configurable

v0.1.39 defines a strong standard reservation form and supplier/internal split. It intentionally **does not** enumerate every supplier-specific field, child-age cutoff, extra dock/tax fee or distant-hotel pickup condition. The developer should provide Admin add/edit/hide/required and supplier visibility controls. Unknown required costs must remain unknown instead of $0. These gaps should not block common bookings. Test new custom field visibility: private by default and never leaked in provider links.

## Approved deferrals — do NOT let these prevent developer review

Wallet aesthetics; Portuguese legal-clause rewriting; in-app e-signing; WhatsApp automation; all historic-record imports or automatic Trello/WhatsApp migration; comprehensive incident/cancellation systems; all conceivable provider/age/hotel exceptions; perfect per-tour allocation of bundled extras; statutory tax accounting. Owner allows manual launch-data entry from Trello/Sheets/WhatsApp and wants to keep the interface very simple.

## Recommended developer handoff sequence

1. **Prepare v0.1.40** as an additive clean checkpoint: current `START HERE` brief, authoritative rewritten current rules, selective propagation/manual-fallback contract, targeted acceptance scenarios and this audit; preserve original workbooks/data and history. **Obtain owner's authorization before building ZIP.**
2. **Developer's first deliverable:** existing-app gap assessment (what works, what is partial, what is missing), security/storage/migration overview, and a prioritized implementation plan. Reuse the app rather than rebuilding.
3. **Developer's first usable milestone:** complete standard customer sale → finalized/versioned contract PDF → arrival → one or more Admin reservations → provider planned costs and recorded real payments → wallet PDF → simple reports, **all with manual corrections and a basic selective impacted-item review** wherever the app derives linked changes. No forced propagation.
4. **Second milestone:** expand selective impact detection to remaining declared dependencies, strengthen automation, complete detailed supplier mappings and security/financial acceptance regressions. This expands P0 capability, not an invitation to postpone it indefinitely.
5. **Owner UAT before launch:** edit and recover from automation failures, test partial updates and paid-record divergence, verify real generated customer/supplier PDFs and supplier-link isolation; then optionally enter existing upcoming bookings manually.

## Scope of verification and limitations

This is a **static-source/document review**, not a legal audit, independent commercial revalidation of supplier prices, production security penetration test, or proof of the partially built application's correct behavior. The four listed P0s are **handoff/engineering clarity gates**, not four new requests to recreate the existing supplier and financial rules from scratch. None requires redoing the source supplier spreadsheets. This report is separate from the ZIP, which remains unchanged.
