# 11 — CURRENT OPERATING CONTRACT: NO-CODE ADMIN, SELECTIVE IMPACTS & MANUAL FALLBACK (v0.1.40)

**Status:** P0 owner-approved architecture requirement, derived from explicit owner discussions through 2026-10-21. This document is the CURRENT rule for edits, source recalculation and continued operation when automation fails. It supersedes contrary historical guidance. **No claim of existing implementation.**

## A. Goal

The **business must remain operable without perfect data or perfect automation.** The owner can correct any operational business value in the app and continue working even when sources, bookings, expenses or documents do not reconcile. The app must be **exceptionally simple** day to day. Engineering quality still protects access, historical signed output, real money movements, stable IDs and referential integrity.

## B. One reusable cross-app change framework — mandatory

1. **Edit source independently.** Admin changes an authorized editable business value (hotel/date/pax, supplier tariff, booking status, pickup, provider, service, cost, effective payable, wallet, note, dynamic field, etc.). The base edit must have a safe save path even if propagation cannot be computed.
2. **Identify dependencies.** The app determines all **declared and computable** affected items across contract/arrival/reservations/payables/wallet/reports/zone selection and historical snapshot surfaces, including indirect effects as dependency rules permit. Do not promise omniscience: if an impact is unknown/uncomputable, explicitly show **Needs manual review**, not a false promise of exhaustive detection.
3. **Preview individually** before applying side effects: field/record description, current value → proposed value, dependency reason, automation/manual override marker, paid/confirmed/signed caution where relevant, and whether it is eligible for automated update. Include no fabricated amounts. **For any selected subset, recompute downstream proposed numbers using that subset, show dependencies/actual kept values, and request explicit manual value if an isolated dependent calculation cannot be derived; never precompute all-selected totals and silently apply them to a sparse subset.**
4. **User-controlled subset:** default to **no automatic changes to manually overridden or protected items**. Admin can choose **zero, any arbitrary subset, or all eligible affected items**, with compact **None** and **All** actions. A confirmed booking can be edited; a previously manually entered destination can be selected explicitly. Unselected values must remain byte-for-byte / semantically unchanged.
5. **Apply only chosen changes**, transactionally where shared financial invariants demand it; journal each actual update with actor/time/old/new/intent/source. Recalculate reporting views off effective records without converting an unpaid liability into a cash movement. Any affected non-selected/differing record gets a targeted nonblocking review cue. **Do not** automatically change the signed contract or issue a new signed PDF.
6. **Manual overrides are sticky** across later triggers until Admin explicitly selects that field for update or restores automation for that field. An explicit one-off update is not automatically permission for every future recalculation; show the intended mode.
7. **Failures and concurrent edits:** recheck record versions/values at commit; do not silently overwrite another user's edit. Show a clear changed-since-preview conflict and allow refresh/reselect. If one selected destination fails, report which applied and which failed, or roll back an all-or-nothing operation; never silently claim all succeeded. Retry by stable idempotency key without duplicate arrivals, bookings, receipts or payables.
8. **Visible attention lifecycle:** revising a finalized sale flags its arrival **Changed / Needs Attention** regardless of which destinations were selected. Important unresolved downstream mismatches produce specific tasks. Admin can review and explicitly **Dismiss** them without forcing perfect reconciliation. Dismissal is itself audited, and later relevant edits can raise a fresh flag.
9. **UI simplicity:** one compact affected-items screen/dialog with per-row optional checkboxes, no repeated warning popups. Display only ordinary relevant data on default screens; use View History for detailed audit and advanced field settings in Admin.

### Example (illustrative only)

A booking's location is edited; possible impacts: supplier zone, Dolphin round-trip transport, supplier effective payable, wallet pickup, finance estimate. Show five old → suggested values and let Admin choose any subset. A previously overridden payable of USD 135 remains USD 135 unless expressly selected; actual paid-cash rows remain unchanged even if effective payable cost is changed. *The five are illustrative, not an asserted universal dependency list.*

### Strict boundaries — not ordinary checkboxes

- **Already issued/signed contract PDFs:** immutable stored version; new revision creates a new version, never mutates prior signed bytes.
- **Cash transaction ledger:** refunds are separate dated money-out; receipt corrections/reversals are auditable and Admin-only. Payment allocations and payable edits do not rewrite the historical cash-out event.
- **Security/identity:** cannot disable required identity keys, authentication/authorization, access isolation, correct provider-link scoping, historic provenance, or integrity of mandatory transaction facts through field builder or propagation controls.
- **Seller access:** seller can finalize/revise contracts and add/view customer receipts, but not supplier reservations, provider cost/credit ledgers, refund/correction tools, cross-company financial reports or Admin configuration. Supplier external access is restricted to **one reservation AND its current provider/recipient**; reassigning providers revokes the former provider’s links and API/file reads/writes immediately. Retrospective disclosure of previously private custom values is prohibited by default.

## C. Manual-first recovery: complete critical workflows without their automations

- Seller may create/finalize a contract even if a supplier rate is unknown, with a **Cost Required** task for Admin; do not claim missing price is zero.
- Admin can independently **create or correct arrivals, dated hotel/service attribution, operational bookings (including separate airport legs), supplier confirmation, supplier rate/transport/ancillary cost, payables/allocations, genuine supplier payments, client receipts/refunds, current wallet fields, and reporting classifications**. No dependent automation may trap data in an unusable state.
- Failure in contract→arrival creation, lookup/mapping, tour-to-supplier linking, cost calculation, provider-link generation, PDF prefill or **PDF rendering/issuance** or readiness calculation must preserve already committed user data and offer a **manual completion path** with precise error and optional safe retry. For PDF failure, support version-linked manually produced DOCX/PDF attachment or safe retry; never forge successful issuance/signature, and never create duplicate arrivals or money entries. Use stable IDs/upserts rather than duplicate 'create' actions.
- An edited field does **not** implicitly alter any source/neighbor record unless Admin selects that exact impact. Reports should show accurate available facts and clear estimates/unknowns; warning states are **not transaction blockers**.
- Provider-side statuses can be set by Admin after WhatsApp/phone confirmation; a supplier link is convenience, not a gate. Provider link revocation/cross-booking privacy must function before public use.
- Wallet can be populated and prepared manually; Ready/Send labels never fabricate supplier confirmation, pickup time or code.
- Manual migration of upcoming arrivals and real receipt history from Trello, Google Sheets and WhatsApp is acceptable. Preserve original dates/native amounts and detect duplicate entries; **automation of migration is not required**.

## D. No-code business configuration (Admin only)

Admin can add/edit/reorder/disable ordinary customizable fields and options in relevant contract, arrival, client, service, supplier reservation and wallet forms; change labels, conditional requirements and supplier visibility; edit catalog tour names/descriptions, supplier rates and zone rules, adult/child/infant Dolphin transportation rates, 2027+ Xcaret high/regular windows/operating calendars, observations and template texts. Keep defaults clean and protect old booked snapshots. **Administrative field additions cannot silently grant data permissions.** The developer must distinguish editable business configuration from code-only security, invariants, and deep new workflows. **Maintain stable custom-field IDs and archived historical versions. Visibility increases apply to new values by default; old private stored values require explicit record-specific Admin disclosure consent; enforce supplier field allowlists on server/API/PDF/attachments, not merely by hiding UI elements.**

## E. Initial client-facing records and supplier-specific rules

- **Each sold service** carries adults, children **and infants** as separate counts where relevant; do not assume all sold services share total party composition. A zero infant count should be explicitly established, not silently inferred from an absent field. Missing base supplier infant tariff remains **Cost Required / Admin review** when relevant; Dolphin transport infant pricing is known separately.
- **Inclusions/exclusions:** some owner-approved description text is missing from all supplier catalogs. Provide Admin-configurable service text, seller/per-contract custom text where permitted, and a missing-copy warning. Do not invent inclusions, exclusions or pricing.
- **Supplier reservation:** unique internal reference separate from supplier confirmation number; name, tour/date, dated hotel, optional room, adults/children/infants, pickup, meeting point, provider, supplier-visible observations, **private staff notes**; Admin custom fields private-by-default and selectable visibility. No supplier gets another reservation/contract/CPF/internal ledger.
- **Dolphin:** 8-zone, per-person, round-trip transport is ON by default for applicable Dolphin reservations, Admin can opt out and change age/zone rates. USD per-person 9.01/12.01/15.02 derived from supplier MXN chart and planning rate 16.65; southern mapping is owner operational default, not supplier eligibility guarantee. Do not double count transport in payable/actual spend.
- **Xcaret 2027+:** all future-year dates selectable until explicit Admin-year restrictions; use current configured costs and an explicitly Admin-selected provisional High/Regular rate when necessary. Never extend 2026 dates or claim confirmed opening. On rate edits, preview applying supplier costs to selected not-yet-commenced arrivals, including already booked ones; agreed customer selling prices and actual historic payments do not automatically change.

## F. Launch testing — non-negotiable evidence

Before owner accepts the first usable build: test five-target changes choosing 0/1/2/3/4/5, manually overridden cost persistence and explicitly chosen update, confirmed/paid divergence warnings, race/conflict resolution, partial failure/retry idempotency, manual missing-arrival recovery, an unknown rate with real payable override, infant transport calculations, multi-hotel dated pickup, signed PDF versions, actual cash refund/reversal, supplier link scope/revocation, custom field data leakage, current wallet, and reports. See `05_Acceptance_Scenarios.md` for written scenarios; **run actual executable tests separately**.
